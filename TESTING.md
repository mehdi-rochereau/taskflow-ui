# Testing Strategy

> 🇫🇷 Une version française suivra avec le rattrapage documentaire.

This document states what is tested in this repository, what is not, and why.
It is written before the tests it describes, so that the plan precedes the work
rather than being reconstructed from it.

---

## Two levels, no more

**Unit tests** cover the logic that carries real risk: pure functions, the HTTP
services, and the authentication chain made of the interceptors, the route guard
and the resolver. They use Vitest, and TestBed only where Angular's injector is
needed.

**Component tests** cover the wiring between a component, its template and its
services. They use TestBed with the real template and Angular Material test
harnesses. HTTP is replaced by `HttpTestingController`, never by a running
backend.

The second level is what this project calls integration. It is the only form of
integration a frontend has. There is no database, no transaction and no
persistence layer here, so transposing the API's notion of an integration test
would be meaningless.

---

## What is deliberately out of scope

**Tests that start the API and a database.** The frontend has nothing to
integrate with at that level. The real cross-boundary risk is contract drift,
where the TypeScript types describe a promise rather than what the network
returns. That risk is answered by a contract test against `/v3/api-docs`, not by
standing up the stack.

**End-to-end browser tests.** They partly duplicate the CD smoke tests and the
production header verification, and they require infrastructure. Possible later,
once the two levels above exist.

**Coverage as a goal.** A frontend contains a large amount of template and
boilerplate whose test cost exceeds its value. The threshold, once introduced,
is set from a measured baseline rather than copied from the API's 95 percent.

---

## Running the tests

```bash
npm test          # single pass, what the CI runs
npm run test:watch # watch loop for local development
```

No backend, no database and no Docker are required. `HttpTestingController`
replaces the network entirely. A suite that needs a backend running is a suite
that stops being run.

The CI executes `npm test` after ESLint and before the production build. The
step is blocking.

---

## Conventions

Specs live beside the file they cover and carry the same base name, so
`form-errors.ts` is covered by `form-errors.spec.ts`.

`describe`, `it`, `expect` and `vi` are global, declared through
`"types": ["vitest/globals"]` in `tsconfig.spec.json`. They are not imported.

The `@angular/build:unit-test` builder generates its own TestBed initialisation,
so there is no manual setup file in this repository.

A test asserts a behaviour, never the mere existence of a symbol. The twenty-eight
specs generated by the Angular CLI were deleted rather than filled: each asserted
`expect(x).toBeTruthy()`, which passes on broken code, and together they gave the
appearance of a complete suite while verifying nothing.

## Tests written because a defect happened

Two entries so far, and this section is meant to grow.

`authInterceptor` is the first priority of the suite. A conflict between it and
`errorInterceptor` on 401 responses reached production once, and the silent
refresh is the mechanism nobody dares touch without a safety net.

`passwordMatchValidator` clears its error on the `confirmPassword` control when
the fields match again. Two empty fields are equal, so that clearing branch runs
on an empty form, and without its `hasError` guard it would erase the `required`
error. A test pins that case.
